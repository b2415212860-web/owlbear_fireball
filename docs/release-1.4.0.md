# 1.4.0 · GM 房间共享残留素材

## 目标

保留每个浏览器按房间保存残留模板的能力，同时允许 GM 发布一份全房间配置。GM 发布后，所有启用同版扩展的客户端立即改用该模板，并把它写回自己的浏览器缓存。

## 数据流

1. 扩展启动时读取 `localStorage` 中当前房间的有效模板。
2. 扩展读取 `OBR.room` 元数据；若存在 GM 发布的有效模板或明确的关闭状态，以房间值覆盖本地状态。
3. 所有客户端通过 `OBR.room.onMetadataChange` 监听后续变化，并同步更新内存与本地缓存。
4. 只有 GM 的界面允许选择或关闭。选择器只读取 GM 自己的素材库，房间元数据仅保存素材 URL、尺寸、DPI、缩放、旋转和名称，不保存图片二进制。
5. 施法开始时快照当前模板。成功经历开始、命中和播放结束后，由施法客户端在命中点创建一个共享 `PROP`。

房间元数据键为 `com.codex.owlbear-fireball/residue/room-template-v1`。键不存在表示 GM 尚未发布，浏览器可继续使用自己的旧缓存；值为 `null` 表示 GM 已明确关闭残留，并会清空客户端缓存。无效值会被忽略，不会破坏现有有效模板。

## 权限

- GM 才能发布或关闭模板；控制器和素材管理器都会复核角色，不能通过伪造本地按钮消息绕过。
- 玩家无需在自己的素材库中拥有 GM 的素材条目，但素材 URL 必须能被该玩家的浏览器访问。
- 残留仍由施法者创建。玩家必须由 GM 在 Owlbear 房间设置中获得 Props 创建权限，即 SDK 的 `PROP_CREATE`。权限不足时只提示残留创建失败，不重播、不回滚火球动画。
- 本版不会尝试由在线 GM 代理创建，也不会修改房间权限。

## 一致性与失败处理

- GM 的房间元数据写入成功后才采用新模板；写入失败保留所有客户端原配置。
- 配置选择、同步和创建不进入渲染循环，不增加 Three.js 粒子、Draw Call 或逐帧 SDK 通信。
- 浏览器禁止本地存储时，房间内当前会话仍可同步和使用模板，但刷新后需再次从房间元数据恢复。
- 场景切换、取消、超时、播放失败或远端观看不会额外生成残留；已有 Props 不受“关闭”操作影响。

## 验收

自动回归覆盖 GM 发布与清除、玩家只读、房间更新覆盖浏览器缓存、无房间键时保留旧缓存、无效配置隔离、房间写入失败回滚、`PROP_CREATE` 允许/拒绝，以及原有施法、场景、渲染和部署流程。真实房间仍需用至少一个 GM 客户端和一个玩家客户端验证素材 URL 的跨客户端可访问性及 Owlbear 权限设置。

本次 TypeScript 检查、173 项单元/流程测试和 6 项 `/fireball/` 部署测试通过。生产构建 manifest 为 1.4.0。Three.js 主特效包体与 1.3.1 相同，仍有 Vite 的 500 kB 体积提示；本次同步功能没有进入渲染 chunk 或增加逐帧工作。
